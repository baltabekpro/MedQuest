## ВВЕДЕНИЕ

Преддипломная практика является важным этапом подготовки специалиста в области программной инженерии, позволяющим применить теоретические знания на практике и получить опыт разработки реальных программных систем.

В ходе преддипломной практики мною была разработана и реализована полнофункциональная CRM-система для медицинского центра под названием **MedQuest**. Проект представляет собой комплексное решение для управления пациентами, медицинскими запросами, пользователями системы и ведения аудита действий.

**Актуальность темы:** В современных медицинских учреждениях остро стоит проблема эффективного управления потоком пациентов, медицинских запросов и координации работы персонала. Автоматизация этих процессов позволяет значительно повысить качество обслуживания пациентов и оптимизировать работу медицинского персонала.

**Цель преддипломной практики:**
- Получить практические навыки разработки полнофункциональных веб-приложений

**Задачи практики:**

### 1.2 Характеристика проекта «MedQuest» <a name="характеристика-проекта-medquest"></a>

**MedQuest** — это CRM-система (Customer Relationship Management) для медицинского центра, предназначенная для комплексного управления:
- **Регистрацией пациентов** — сохранение и управление данными пациентов (ФИО, дата рождения, контакты, адрес)
- **Управлением медицинскими запросами** — создание, отслеживание и управление запросами пациентов
- **Назначением врачей** — распределение запросов между специалистами
- **Контролем статусов** — отслеживание прогресса выполнения запросов
- **Анализом статистики** — просмотр ключевых показателей на панели управления
- **Ведением аудита** — логирование всех действий в системе для контроля и безопасности

Система разработана для использования в медицинских центрах с небольшим количеством сотрудников и может быть адаптирована под более крупные организации.

### 2.1 Анализ текущего состояния и архитектура <a name="анализ-текущего-состояния-и-архитектура"></a>

Архитектура системы состоит из трех основных уровней, где Frontend (SPA) взаимодействует с FastAPI сервером, который обращается к базе данных через ORM (трехслойная архитектура).

### 2.2 Разработка Backend-архитектуры и базы данных <a name="разработка-backend-архитектуры-и-базы-данных"></a>

Все запросы валидируются на стороне сервера модулем Pydantic: проверка типов, длины строк.
Настроены миграции через Alembic, что позволило гибко управлять схемой базы данных.

### 2.4 Настройка системы ролей и прав доступа <a name="настройка-системы-ролей-и-прав-доступа"></a>

В системе реализовано 3 роли:
1. **Администратор** - полный доступ, может редактировать пользователей и просматривать аудит.
2. **Регистратор** - добавление пациентов, работа с карточками и назначение запросов врачам.
3. **Врач** - отображение только своих запросов, смена статуса на "В работе" или "Закрыт", написание комментариев.

Каждый запрос к API защищен JWT-токеном, и происходит проверка роли (Role-Based Access Control) на стороне бэкенда.

### 5. Система комментариев

**Описание:** Взаимодействие между врачом и другими сотрудниками по запросу.

**Функции:**
- Добавление комментариев к запросу
- Просмотр истории комментариев
- Отображение автора и времени комментария
- Редактирование собственных комментариев

### 6. Управление пользователями

**Описание:** Управление сотрудниками системы (доступно только администраторам).

**Функции:**
- Просмотр списка всех пользователей
- Добавление новых пользователей
- Назначение ролей
- Активирование/деактивирование аккаунтов
- Редактирование данных пользователя
- Удаление пользователей

**Роли:**
- **Администратор** — полный доступ
- **Регистратор** — управление пациентами и запросами
- **Врач** — работа с назначенными запросами

### 7. Система аудита

**Описание:** Логирование и просмотр всех действий в системе.

**Отслеживаемые действия:**
- Создание/редактирование пациентов
- Создание/изменение запросов
- Смена статусов
- Добавление комментариев
- Управление пользователями
- Вход/выход из системы

**Информация в логе:**
- Пользователь (кто)
- Действие (что)
- Дата и время (когда)
- Затронутый объект (где)
- Детали изменений

### 8. Уведомления

**Описание:** Система для информирования пользователей о важных событиях.

**Типы уведомлений:**
- Новый запрос назначен врачу
- Запрос изменил статус
- Добавлен комментарий к запросу
- Новый пользователь создан

## СТРУКТУРА ДАННЫХ

### Таблица Users (Пользователи)

```
id: INTEGER (PRIMARY KEY)
email: VARCHAR (UNIQUE) — электронная почта
full_name: VARCHAR — полное имя
hashed_password: VARCHAR — хешированный пароль
role: ENUM (admin, registrar, doctor) — роль пользователя
is_active: BOOLEAN — статус активности
created_at: DATETIME — дата создания
```

### Таблица Patients (Пациенты)

```
id: INTEGER (PRIMARY KEY)
full_name: VARCHAR — полное имя пациента
date_of_birth: DATE — дата рождения
phone: VARCHAR — номер телефона
email: VARCHAR — электронная почта
address: VARCHAR — адрес проживания
created_at: DATETIME — дата регистрации
created_by: INTEGER (FK → Users) — кто создал запись
```

### Таблица PatientRequests (Медицинские запросы)

```
id: INTEGER (PRIMARY KEY)
patient_id: INTEGER (FK → Patients) — пациент
title: VARCHAR — название запроса
description: TEXT — полное описание
status: ENUM (new, in_progress, closed) — статус
priority: INTEGER (1-5) — приоритет
assigned_doctor_id: INTEGER (FK → Users) — ответственный врач
created_at: DATETIME — дата создания
created_by: INTEGER (FK → Users) — кто создал
updated_at: DATETIME — дата последнего изменения
```

### Таблица RequestComments (Комментарии)

```
id: INTEGER (PRIMARY KEY)
request_id: INTEGER (FK → PatientRequest) — к какому запросу
user_id: INTEGER (FK → Users) — автор комментария
text: TEXT — текст комментария
created_at: DATETIME — дата создания
```

### Таблица AuditLogs (Журнал аудита)

```
id: INTEGER (PRIMARY KEY)
user_id: INTEGER (FK → Users) — кто выполнил действие
action: VARCHAR — тип действия
entity_type: VARCHAR — тип объекта
entity_id: INTEGER — ID объекта
details: JSON — дополнительные детали
created_at: DATETIME — когда произошло действие
```

### Таблица NotificationStates (Уведомления)

```
id: INTEGER (PRIMARY KEY)
user_id: INTEGER (FK → Users) — адресат
request_id: INTEGER (FK → PatientRequest) — связанный запрос
type: VARCHAR — тип уведомления
message: TEXT — текст уведомления
is_read: BOOLEAN — прочитано ли
created_at: DATETIME — дата создания
```

## БЕЗОПАСНОСТЬ

### Реализованные механизмы защиты

1. **Аутентификация (JWT токены)**
   - Каждый запрос должен содержать валидный JWT токен
   - Токен генерируется при входе в систему
   - Содержит информацию о пользователе и его роли
   - Срок действия: настраивается в конфигурации

2. **Авторизация (проверка прав)**
   - Система проверяет роль пользователя перед доступом
   - Разные роли имеют разные права доступа
   - Проверка прав происходит на уровне API

3. **Хеширование паролей**
   - Пароли не хранятся в открытом виде
   - Используется криптографическое хеширование (bcrypt)
   - Пароли проверяются при входе

4. **Валидация входных данных**
   - Все данные проверяются перед обработкой
   - Проверяются типы, формат, диапазоны значений
   - Использует Pydantic для валидации

5. **Журнал аудита**
   - Все действия логируются в БД
   - Сохраняется информация о пользователе, действии, времени
   - Невозможно скрыть или изменить старые логи

6. **CORS (Cross-Origin Resource Sharing)**
   - Настроено взаимодействие между Frontend и Backend
   - Только разрешённые источники могут обращаться к API
