# MedQuest Backend — Задачи по доработке API

Ниже описаны все расхождения между дизайном фронтенда и текущей спецификацией
`swagger.yml`. Каждый пункт — конкретная задача с описанием, что сделать и почему.

---

## 1. DashboardStats — добавить `requests_closed_today`

**Где:** `GET /dashboard/stats` → схема `DashboardStats`

**Проблема:** дизайн Dashboard показывает карточку «Закрыто сегодня» (число закрытых запросов 
за текущий день). В текущей схеме есть только `requests_closed` (общее число за всё время).

**Что сделать:** добавить поле `requests_closed_today: int` в `DashboardStats` и в расчёт 
в эндпоинте.

---

## 2. Pagination — все списки должны возвращать пагинированный ответ

**Где:** `GET /patients`, `GET /requests`, `GET /users`, `GET /audit/logs`

**Проблема:** все эндпоинты возвращают голый массив. Дизайн везде показывает
«Показано 1–8 из 248», «Показано 1–7 из 82», «Показано 1–20 из 2450».
Frontend не может построить пагинацию без знания `total`.

**Что сделать:**
- Добавить query-параметры `page: int = 1` и `limit: int = 20` ко всем список-эндпоинтам.
- Изменить тип ответа: вместо `array` возвращать объект:
  ```json
  {
    "items": [...],
    "total": 248,
    "page": 1,
    "limit": 20
  }
  ```
- Создать переиспользуемую generic-схему `PaginatedResponse[T]`.

---

## 3. Поиск и фильтрация пациентов

**Где:** `GET /patients`

**Проблема:** страница «Пациенты» имеет строку поиска «Поиск по ФИО, телефону, email...».
Текущий эндпоинт не принимает никаких query-параметров для поиска.

**Что сделать:** добавить query-параметры:
- `search: str | None` — поиск по `full_name`, `phone`, `email` (ILIKE)

---

## 4. Расширенная фильтрация запросов

**Где:** `GET /requests`

**Проблема:** страница «Запросы» имеет фильтры по статусу, приоритету, врачу, дате,
и поиск по тексту. Также карточка пациента показывает его запросы — нужна фильтрация по `patient_id`.
Текущий эндпоинт принимает только `status` и `assigned_doctor_id`.

**Что сделать:** добавить query-параметры:
- `patient_id: int | None` — для карточки пациента
- `priority: int | None` — фильтр по приоритету (1–5)
- `date_from: date | None` — начало диапазона дат
- `date_to: date | None` — конец диапазона дат
- `search: str | None` — поиск по `title`, `description`

---

## 5. Поиск и фильтрация пользователей

**Где:** `GET /users`

**Проблема:** страница «Пользователи» имеет строку поиска и вкладки по ролям
(Все / Администраторы / Регистраторы / Врачи). Эндпоинт не принимает никаких параметров.

**Что сделать:** добавить query-параметры:
- `search: str | None` — поиск по `full_name`, `email`
- `role: str | None` — фильтр по роли (`admin`, `registrar`, `doctor`)

---

## 6. Расширенная фильтрация аудита

**Где:** `GET /audit/logs`

**Проблема:** страница «Аудит» имеет фильтры по дате, пользователю, типу действия,
сущности и текстовый поиск, а также пагинацию (показано из 2450). 
Текущий эндпоинт принимает только `user_id` и `entity_type`.

**Что сделать:** добавить query-параметры:
- `action: str | None` — фильтр по типу действия (`CREATE`, `UPDATE`, `DELETE`, `LOGIN`)
- `date_from: datetime | None`
- `date_to: datetime | None`
- `search: str | None` — поиск по `details` / описанию
+ пагинация (см. пункт 2)

---

## 7. AuditLogResponse — добавить IP-адрес и имя пользователя

**Где:** схема `AuditLogResponse`

**Проблема:** дизайн аудита показывает колонки «IP-адрес» и «Пользователь (аватар + имя)».
Текущая схема содержит только `user_id` (int) без имени, и не содержит `ip_address`.

**Что сделать:**
- Добавить поле `ip_address: str | None` в `AuditLogResponse` и сохранять его при записи.
- Добавить поле `user_full_name: str` (денормализованное ФИО из User) — либо вложенный объект
  `user: { id, full_name, role }` вместо `user_id`.

---

## 8. PatientRequestResponse — добавить вложенные имена

**Где:** схема `PatientRequestResponse`

**Проблема:** все списки запросов показывают имя пациента и имя врача непосредственно в строке.
Сейчас возвращаются только `patient_id: int` и `assigned_doctor_id: int | None`.
Frontend вынужден делать N+1 запросов или хранить словарь.

**Что сделать:** добавить к `PatientRequestResponse` поля:
- `patient_full_name: str` — денормализованное ФИО пациента (из JOIN при запросе)
- `assigned_doctor_full_name: str | None` — ФИО врача

---

## 9. PatientResponse — добавить имя создавшего пользователя

**Где:** схема `PatientResponse`

**Проблема:** карточка пациента показывает «Добавил: Смирнов А.И.».
Сейчас возвращается только `created_by_id: int`.

**Что сделать:** добавить поле `created_by_full_name: str` в `PatientResponse`.

---

## 10. Отсутствует `GET /users/{user_id}`

**Где:** раздел Users

**Проблема:** нет эндпоинта для получения одного пользователя по ID.
Нужен для: редактирования, просмотра профиля, логики «Сменить врача» в карточке запроса.

**Что сделать:** добавить эндпоинт:
```
GET /users/{user_id}
→ 200 UserResponse
→ 404 если не найден
```

---

## 11. Обновление собственного профиля — `PATCH /auth/me`

**Где:** страница «Мой профиль»

**Проблема:** страница «Профиль» позволяет редактировать ФИО текущего пользователя.
`GET /auth/me` есть, но нет эндпоинта для обновления.

**Что сделать:** добавить:
```
PATCH /auth/me
Body: { "full_name": "string" }
→ 200 UserResponse
```

---

## 12. Смена пароля — `POST /auth/change-password`

**Где:** страница «Мой профиль» → секция «Безопасность»

**Проблема:** форма смены пароля (текущий → новый → подтверждение) не имеет соответствующего
эндпоинта.

**Что сделать:** добавить:
```
POST /auth/change-password
Body: { "current_password": "string", "new_password": "string" }
→ 200 { "message": "Password changed" }
→ 400 если текущий пароль неверен
→ 422 если новый пароль не соответствует требованиям
```

---

## 13. История входов — `GET /auth/sessions`

**Где:** страница «Мой профиль» → секция «Активность»

**Проблема:** таблица «Активность» показывает последние 5 входов с датой, IP-адресом,
устройством, статусом (Успешно / Отклонено). Нет ни такого эндпоинта, ни такой модели.

**Что сделать:**
1. Создать модель `LoginEvent` (`id`, `user_id`, `timestamp`, `ip_address`, `user_agent`,
   `success: bool`) и таблицу в БД.
2. Сохранять событие при каждом вызове `POST /auth/login` (успешном и неуспешном).
3. Добавить эндпоинт:
   ```
   GET /auth/sessions
   → 200 array of LoginEventResponse (последние 20, desc по timestamp)
   ```

---

## 14. Выход из системы — `POST /auth/logout`

**Где:** кнопка «Выход» в боковой панели

**Проблема:** нет эндпоинта для инвалидации refresh-токена. Кнопка «Выход» только
удаляет токен на клиенте, но на сервере он остаётся валидным.

**Что сделать:** добавить:
```
POST /auth/logout
Body: { "refresh_token": "string" }
→ 200 { "message": "Logged out" }
```
Хранить список инвалидированных токенов (blocklist в памяти или в БД) или использовать 
короткий TTL access-token + хранение refresh-токенов в БД с флагом `revoked`.
